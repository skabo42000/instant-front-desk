# Local ingestion and retrieval (prototype)

Milestone 5, 2026-10-10. This is offline fixture evidence, not a live-site evaluation.
No provider calls, customer results or deployment are demonstrated here.

## Load a website in the local browser (October 22, 2026)

On the loopback home page, enter an approved public website in **Add a website**
and click **Load website**. Keep the page open; it shows a loading message and
opens `/b/<slug>` when finished. This usually takes about a minute, but crawling
can take up to the existing two-minute cap, followed by embedding calls. This is
fixture-tested prototype behavior; no new live-site validation was run for this UI.

This form requires `LOCAL_CHAT_MODE=real`, `FREE_TIER_CONFIRMED=yes`, local PGlite
storage and existing evaluation keys. It is hidden if `IFD_PILOT_MODE=yes` **or an
invitation token is configured**, including a dormant token saved for pilot setup.
The local server must start without `PILOT_ACCESS_TOKEN` to use the form. Do not
clear an active pilot's token or change its policy. The new endpoint also returns
404 for those configurations, public/LAN hosts or non-loopback forwarding headers.
It accepts Next's direct loopback forwarding headers and requires the browser's
exact local Origin for POSTs. Keep the existing loopback server binding; header
checks are not a replacement for a network boundary.

The box uses `/api/ingest` in the server process and reuses its open PGlite
connection. **Do not run a database CLI while the server is running.** Local
storage is selected by `IFD_DATABASE_DIR` (or the existing default); merely setting
`IFD_DATABASE_URL` does not select Postgres. `IFD_DATA_STORE=postgres` selects the
separate restricted pilot read path and disables browser ingestion.

The submitted address is normalized to the exact origin's root, removing its
path, query and fragment. Ingestion reuses `ingest`, the crawler and safe fetch,
with the unchanged 15-page, depth-2, 30-request, 1 MiB response, 10 MiB total and
120-second crawl caps. Robots, redirect validation, public-address DNS checks and
exact-origin traversal remain enforced. The box explicitly selects a tolerant
policy: child pages that redirect off-site, fail, return non-200/non-HTML or are
robots-disallowed are recorded as skipped. Empty pages are not counted as readable.
Page, total request, byte or time limits stop collection and mark it truncated;
the crawler never fetches beyond its existing safety boundary. The first readable
pages are kept in breadth-first order. Robots fetch failures (except 404), robots
denial of the start URL, and start-page fetch/redirect failures still reject the
load. Zero readable pages also rejects it.

A successful tolerant load with at least one readable page replaces the box
business's snapshot, even when pages were skipped or collection was truncated.
Fatal fetch errors or embedding/budget failures preserve its last good snapshot.
An empty/failed first load may leave an empty business record. **CLI ingestion and
evaluation callers retain strict behavior by default**, rejecting partial crawls;
their output shapes and snapshot rules are unchanged.

The API returns `{location, pages, skipped, truncated}` with counts, never raw
page errors. After redirect, the chat page shows a plain-English note with pages
loaded, skipped pages and any truncation. This feedback is bounded local process
memory (up to 100 sites), disappears on server restart, and is hidden in pilot
mode. It is a crawl summary, not a quality-test result.

Unlike the practice CLI below, the form selects **the shared chat runtime's
`gemini-embedding-001` adapter at 768 dimensions**. Website chunks now use
`batchEmbedContents`, with at most 100 texts and 1 MiB of serialized JSON per
request. A normal 93-chunk site uses **one embedding call**, rather than 93;
the fictional two-page/three-chunk fixture also uses one call. Unusually large
headings can require smaller batches to stay within the byte cap. Both batches
and single chat-query calls retain the existing unspecified task type; no new
document/query task setting or vector space is introduced. Chat queries still
use `embedContent`. Repeated loads embed again. No questions, quality tests or
judge calls are generated by loading.
Chat subsequently uses the same adapter/vector space; a new site says
“No quality test yet for this site”. Browser-added business IDs include origin
and embedding model so old practice CLI data and saved evaluations are preserved.

Embedding and answer requests share the existing process-wide call cap
(`LOCAL_CHAT_MAX_CALLS`, default 60) and provider quota stop. There is no paid
fallback or new key. After crawling/chunking, before any embedding call or
snapshot replacement, the runtime counts all required batches and holds their
process-call slots. If they will not fit, the load is refused without consuming
calls or stopping chat for other sites. Unused held slots are released on failure.
Each attempted batch reserves the existing shared budget once, including when
the runtime uses `PostgresProviderBudget`. A local cap refusal does not write a
quota stop. An actual provider quota response still stops further calls and uses
the existing stop persistence. The local safety cap is not a daily-reset counter,
and tomorrow alone may not clear a provider quota stop.
Operator review is required before resuming; this UI has no reset control. Pilot
persistent budget/stop behavior is unchanged and ingestion is unavailable there.
Only one browser load runs at once, including across tabs; another request gets
a friendly wait message.

attempt, not evidence of learning.

## Practice CLI

For a site Bosko has approved, run:

```powershell
npm run ingest -- https://approved-site.example/
```

The command uses the existing crawler and safe fetch boundary, including robots,
exact-origin traversal, private-address blocking and resource caps. It stores a
local PGlite database under ignored `data/instant-front-desk`. A business is keyed
by its origin, so repeated commands use the same business. Ingest the site's root
URL to get its intended page scope. The command replaces the business's current
page snapshot; ingesting a narrower entry point can remove previously stored pages.
Incomplete crawls are rejected without replacing a successful snapshot. A newly
created business may remain empty when its first crawl fails.

Chunks stay within a heading section, have at most 800 characters of text and
approximately 80 characters of overlap. SHA-256 hashes determine stable chunk
UUIDs from page URL, ordinal, heading and text. Repeated unchanged ingestions keep
page/chunk counts and citation IDs stable. Crawl runs are separate audit records.
Changed pages remove obsolete chunks in the same transaction. Existing evaluation
foreign keys can block removing cited chunks; that safely rolls back ingestion
rather than silently breaking saved citations. Versioned evidence is future work.

The fake adapter hashes tokens into normalized vectors; it measures token overlap,
not semantic meaning. Every chunk stores model and dimension metadata. This local
schema accepts 768 dimensions only; a real model with another size needs a schema
migration and re-embedding, never a mixed-space fallback.

`retrieve(question, repository)` returns `status`, `chunks` in the shape accepted
by `answer`, and contacts extracted literally from current page text, with page
URLs. Contacts are separate from relevant answer chunks, so an unsupported query
can still show a sourced contact without treating it as answer evidence. Retrieval
defaults to five nearest chunks and a maximum Euclidean distance of 1.25 on fake
normalized vectors. No close chunks produces `insufficient evidence`. Real-model
thresholds require separate calibration in milestone 10. Literal contact extraction
does not establish that a website's claims are true or that hostile text is safe.

Offline checks:

```powershell
npm run typecheck
npm run test
```

The database tests use actual in-memory PGlite/pgvector, not a mocked repository.
They do not verify multi-connection Postgres concurrency. In a restricted Windows
sandbox, set `TEMP` and `TMP` to an ignored `data/test-temp` folder if Vitest cannot
write to the system temporary directory.

Beginner explanation: ingestion stores small website excerpts; retrieval selects
nearby excerpts for one business. Stable IDs let answers cite the same unchanged
excerpt after another crawl.
